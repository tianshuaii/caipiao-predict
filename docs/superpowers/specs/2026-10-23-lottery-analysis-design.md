# 彩票分析与预测程序设计

日期：2026-10-23

状态：供用户审阅；本轮仅整理设计，不实施程序、不启动数据库、不配置定时任务、不发送微信。

## 1. 目标与已确认范围

构建本地运行的大乐透、双色球数据分析与预测程序。采集完整官方历史开奖资料，每周一、三、五北京时间 08:00 更新数据、核对历史预测中奖情况、开展分析、预测下一次尚未开奖的期次，并通过 Server 酱发送微信通知。所有正式预测和后续评价均可追溯。

前端与后端是两个独立项目，各自管理依赖、配置、启动和构建；暂放在同一个工作目录下。前端使用 React 和 HeroUI。MySQL 使用 Docker，宿主机端口 9999。

程序可靠运行与策略研究效果分开验收。不承诺预测逐期改善或稳定超过随机选号；策略结论允许为“没有足够证据优于随机”。

## 2. 本设计采用的默认约定

- “画板”解释为数据仪表盘，包括最近 20 期数据、预测和复盘展示。
- 每次正式推荐大乐透 5 注单式、双色球 5 注单式；同一彩种、同一期去重。不追加、不倍投。第一版不生成复式。
- 单人本地使用，前后端及数据库仅绑定本机地址，不设计账号系统。
- 预测记录不代表实际购买；中奖金额及收益均标记为模拟结果，按对应期官方公布单注奖金和适用规则计算，不代表实际到账金额。
- 第一版不依赖大模型 API。统计分析、训练、选号和结算由代码完成；知识库提供方法与解释依据。
- 每次定时任务合并发送一份两彩种报告，异常状态在报告内明确展示。

## 3. 技术方案与项目边界

### 前端项目：frontend

React 19、TypeScript、Vite、HeroUI 3、Tailwind CSS 4；图表使用 Recharts。具体依赖版本在实施时核验兼容性并锁定。

按业务组织页面和组件：dashboard（概览）、draws（开奖历史）、predictions（预测与复盘）、experiments（实验评价）、tasks（运行状态）。公共接口客户端、类型和基础展示组件集中管理。

前端只调用后端 API，不持有数据库或 Server 酱凭证，不承担定时任务和结算计算。

### 后端项目：backend

Python、FastAPI、SQLAlchemy、Alembic、HTTPX；数据分析使用 NumPy、pandas、SciPy、scikit-learn。定时调度采用 APScheduler，作为独立于 API 的单进程任务入口运行，避免 API 多进程或开发热重载重复触发任务。

按职责划分 api、collectors、analysis、prediction、evaluation、notifications、jobs、models。API 层负责参数校验和查询，业务计算放在对应模块，不堆在路由文件中。

后端提供全量采集、增量更新、滚动回测和执行一期工作流的命令行入口，定时任务复用相同业务逻辑。

MySQL 使用 Docker Compose 和持久化数据卷，映射为 127.0.0.1:9999:3306。应用账户与初始化管理账户分离。配置通过环境变量加载；密钥不提交、不返回前端、不记录到日志。

工作目录结构：

```text
  backend/         # 独立后端项目及数据库迁移

```

## 4. 官方数据与完整性

大乐透以中国体育彩票为主源，双色球以北京福彩为主源。允许中国福彩网及其他官方来源补缺和交叉校验。正式采集前需验证官方入口、接口可用性和实际历史覆盖范围；搜索结果摘要不作为入库依据。

历史范围是各彩种发行首期至最新官方公布期次。首次采集生成覆盖报告，列明起止期次、数量、缺失期次及原因。不能仅以抓取成功或达到某个总数宣称全量完成。

标准化保存彩种、期号、开奖日期、分区号码、各奖级中奖注数及单注奖金；销量、奖池可作为辅助字段。金额使用十进制定点数，缺失奖金不能按零处理。

每次采集保存来源地址、抓取时间、原始响应、内容校验值和解析器版本。区分开奖日期、来源发布时间（如可得）与实际抓取时间。原始响应与解析结果可关联追踪。

以彩种和期号识别开奖记录，检查合法号码范围、数量、区内重复和日期。按年度及官方日历核查缺期，处理跨年和休市，不能对期号简单连续加一。

同一结果的重复抓取不重复创建开奖记录；官方更正保存修订记录。多源冲突不得静默覆盖，标记待核验并暂停该彩种依赖此结果的正式结算和预测；另一彩种可独立继续。

保存历史奖级、玩法和派奖规则及生效范围。预测所需数据与结算所需数据分别检查：开奖号码完整但奖金尚未公布时，旧预测可先记录命中，金额保持待结算，不因此阻止合法的下一期预测。

## 5. 每周工作流

调度时区为 Asia/Shanghai，周一、三、五 08:00 执行。

正常日历的目标期：周一预测大乐透周一、双色球周二；周三预测大乐透周三、双色球周四；周五预测大乐透周六、双色球周日。实际期号、日期和销售截止以官方信息为准，休市或延期优先遵循官方公告。

工作流顺序：

1. 创建持久化任务记录并取得互斥执行权，避免同时执行相同工作流。
2. 拉取最新已开奖数据，并补齐自上次执行以来的所有遗漏期次。
3. 对所有已开奖且尚未完成核对的正式预测计算分区命中数、奖级和模拟金额；记录本次复盘分析。
4. 检查各彩种最新数据是否完整、目标期是否明确且仍可销售。
5. 用当前正式策略和已知数据为各彩种生成 5 注去重单式号码，并保存完整预测批次。
6. 根据已入库结果生成合并报告，通过 Server 酱发送微信，并保存推送状态。

同一期已有正式预测时返回原批次，不能因任务重试而重新抽号或覆盖。没有新增目标期时不重复推荐同一期。已过销售截止时间的期次不得事后补记正式预测。

采集失败进行有限次数退避重试；关键数据缺失时暂停受影响彩种的预测，并在报告中说明。另一彩种的结果可以正常保存、展示和通知。系统不将缺失预测计为未中奖。

通知失败仅重试通知，不重新训练、选号或结算。对响应不明的发送标记为状态不确定；外部通道无法保证绝对只送达一次，消息携带报告编号便于识别重复。

重启后核查漏执行任务，先补数据和旧预测结算，再对仍未截止的目标期生成缺失预测。初次运行没有历史正式预测时，明确报告“无待复盘预测”。

## 6. 预测、知识库与实验

知识库包括概率论与组合数学、统计推断、数据处理、实验与回测、机器学习。每种方法记录公式、前提、用途和局限，并链接到对应实现和实验结果。不为文档存储额外引入向量数据库。

第一版建立均匀随机基线、简单平滑频率候选策略及正则化概率模型的实验流程。正式使用的策略由样本外评价决定；没有可靠优势时保留均匀随机基线，并如实展示。

所有候选策略采用相同的号码约束与最终注数。号码边际概率不能直接解释为整注中奖概率；需要组合概率时必须使用适用的组合模型。单期内抽取存在不放回约束，不能将各号码当作独立事件简单相乘。

训练、调参、概率校准按时间分别划分数据；滚动回测只使用目标开奖前已可得的信息。历史回测、前瞻正式预测分开存储和展示，不能将回测结果包装成当时真实发布的预测。

概率质量以 Brier 分数等预先指定指标及校准结果评价，选号效果报告分区命中分布、奖级、模拟成本与收益。采用同注数、同成本的多次随机模拟建立比较区间，并控制多重试验造成的虚假优势。

逐期更新结果、分析误差和累计表现；候选模型每月离线评估一次。模型晋升标准必须在运行实验前明确并版本化。未完成正式评价协议时不自动替换策略；不能因某一期中奖或未中奖直接调参并声称改善。

## 7. 存储与可复现性

数据按以下实体组织，具体表结构在实施计划中细化：

- 开奖记录、奖项明细、规则版本及来源修订。
- 原始采集响应和采集执行记录。
- 模型与策略版本、实验配置、回测结果。
- 正式预测批次、每注号码、命中及结算记录。
- 定时任务与通知记录。

每个正式批次保存彩种、目标期号及开奖日期、生成时间、数据截止期号、数据版本、策略及代码版本、参数、随机种子、模型文件校验值、概率或评分、最终号码、注数和模拟成本。

正式预测一经生成保留原样。开奖更正触发结算修订，不改写原预测；修订前后结果可查。模型文件和数据快照应有稳定定位信息，并随备份一起保存。

## 8. 前端仪表盘

默认概览同时展示两个彩种：最新已开奖期、下一预测期、各 5 注号码、上期模拟中奖汇总、数据更新时间和任务状态。

最近 20 期视图可切换彩种，展示期号、开奖日期、分区号码、当期正式预测是否存在、命中情况和模拟奖金。红蓝球及大乐透前后区使用明确标记；不能仅靠颜色表达含义。

历史开奖记录允许分页查看更早数据，最近 20 期只是默认展示范围。历史全量数据不一次性传给浏览器。

预测与复盘视图展示每注号码、命中高亮、奖级、模拟金额、批次生成时间、输入截止期、策略版本及来源。提供累计成本、模拟奖金、净收益和相对随机基线的评价。实验数据不足时展示“样本不足”，不显示伪精确的成功率。

实验视图展示策略对比、训练与评估区间、正式策略版本和结论；任务视图展示采集、缺期、冲突、通知失败等状态。数据未到齐、待结算和没有预测均有独立空状态。

前端默认在本机打开。微信消息包含完整核心结果，不依赖手机访问电脑的 localhost 网页。

## 9. Server 酱消息

选择支持微信通知的 Server 酱 Turbo 通道。SendKey 在部署联调时由用户配置进后端本地环境，不在聊天中索取明文。

每份报告包含报告编号、生成时间、数据截止期号；两个彩种各自的上期开奖号码、逐注命中与奖级、模拟奖金汇总；下一预测期号、开奖日期及 5 注号码；简短分析和异常说明。

内容超过通道长度限制时，保持期号、10 注完整号码和复盘核心结果，缩短分析文字。实际限制和账号通道能力在联调时核验；必要的分段使用相同报告编号。

发送服务接受请求与用户实际收到消息分别验证。首次联调需确认微信端收到完整报告；此设计阶段不发送消息。

## 10. 本地运行、备份与验收

本地电脑、Docker 和后端调度进程需在计划时间运行且联网；休眠关机期间不能保证准点发送。恢复后按补跑规则执行，不伪造原定时间的预测。

提供数据库及模型文件的备份、恢复说明，实施时至少演练一次恢复。持久化数据卷不能替代备份。

重点验收：

1. 官方来源覆盖报告可核查，缺期、冲突及辅助数据缺失明确展示。
2. 重复抓取不重复入库，同期重复执行不覆盖预测，通知失败不改变选号。
3. 每彩种每期恰好 5 注合法且唯一的单式号码，均在销售截止前生成。
4. 奖级和奖金按对应历史规则正确结算，包括规则变更、派奖和待结算情形。
5. 能用保存的数据、模型、参数及随机种子重现一次正式预测。
6. 回测不使用未来数据；随机基线和候选策略预算一致。
7. 周一、三、五调度、休市、延期、跨年、断网和重启补跑行为符合设计。
8. 前端最近 20 期、预测、复盘和状态与数据库一致，未定义数据不显示为零。
9. 微信端收到两个彩种各 5 注及正确复盘信息，凭证不出现在前端或日志中。
